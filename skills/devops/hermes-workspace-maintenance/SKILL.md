# Hermes Workspace Maintenance

Update, restart, and troubleshoot the Hermes Workspace web UI (`/root/hermes-workspace`).

## Architecture

| Component | Port | Tmux Session | Healthcheck |
|---|---|---|---|
| Workspace UI | 3333 | `hermes-workspace` | `curl http://127.0.0.1:3333/` |
| Dashboard | 9119 | `hermes-dashboard` | `curl http://127.0.0.1:9119/` |
| Gateway | 8642 | (hermes-agent service) | `curl http://127.0.0.1:8642/health` |
| Nginx proxy | 80/443 | — | `https://hermes.rachkun.dev` → :3333 |

Watchdog: `cron */5 ensure-hermes-workspace.sh` (manages both tmux sessions).

## Update Procedure

```bash
cd /root/hermes-workspace

# 0. Check Hermes Agent version BEFORE updating workspace.
#    Workspace v2.3.0+ may require a recent agent. If >50 commits behind:
hermes --version
#    → if "X commits behind", run: hermes update

# 1. Reset auto-generated files that may conflict
git checkout -- src/routeTree.gen.ts

# 2. Pull
git pull origin main

# 3. Install deps (if any changed)
pnpm install

# 4. After pull, re-check hermes compatibility
hermes --version
#    → update if still behind

# 5. Restart (see below)
```

### Why reset `routeTree.gen.ts`?

This file is auto-generated by TanStack Router. It frequently has local modifications from previous builds and will block `git pull`. Safe to discard — the new version will have the correct generated routes.

## Restart Procedure

**Critical:** tmux does NOT inherit the caller's environment. Inline `PORT` and any other env vars.

The current production config includes all required env vars:

```bash
# Kill
tmux kill-session -t hermes-workspace

# Start (use background=true in terminal tool to avoid foreground detection)
# background=true
cd /root/hermes-workspace && \
  tmux new-session -d -s hermes-workspace -x 160 -y 48 \
    "HERMES_WORKSPACE_DIR=/root/projects \
     CLAUDE_KANBAN_BACKEND=claude \
     HERMES_PASSWORD='!123AdminHermes' \
     TRUST_PROXY=true \
     PORT=3333 \
     pnpm dev 2>&1 | tee logs/workspace.log"
```

Wait ~8s then verify: `curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:3333/` → 200.

### Env Var Reference

| Var | Purpose | Required |
|---|---|---|
| `PORT=3333` | Listen port | Yes |
| `HERMES_WORKSPACE_DIR=/root/projects` | Workspace root (bypass `/root` block) | Yes (on root-user VPS) |
| `CLAUDE_KANBAN_BACKEND=claude` | Force direct SQLite kanban backend | Yes (no dashboard kanban plugin) |
| `HERMES_PASSWORD=...` | Enable password auth on workspace | Optional (but recommended) |
| `TRUST_PROXY=true` | Trust `X-Forwarded-For` from nginx (needed for auth to work on domain) | Required if `HERMES_PASSWORD` is set |

## Workspace Password Auth (v2.3.0)

The workspace has its own password-based session authentication. When enabled, API routes (`/api/*`) require a valid session token, and the frontend shows a login screen.

### How It Works

- **Password-only** — no username. Set `HERMES_PASSWORD` (or legacy `CLAUDE_PASSWORD`) env var.
- Login flow: `POST /api/auth` with `{"password":"..."}` → returns `Set-Cookie: claude-auth=<token>` (HttpOnly, SameSite=Strict, 30-day TTL).
- Rate limit: max 5 attempts per minute per IP.
- Tokens persist to `~/.hermes/workspace-sessions.json` (survive restarts).

### TRUST_PROXY Requirement

Without `TRUST_PROXY=true`, the workspace ignores `X-Forwarded-For` headers from nginx. All requests appear to come from `127.0.0.1` (nginx's local proxy connection), which `isLocalRequest()` classifies as "local" — bypassing auth entirely. **Always set `TRUST_PROXY=true` together with `HERMES_PASSWORD`** when behind nginx.

### Enabling Auth

```bash
# Add both env vars when starting the workspace
HERMES_PASSWORD='your-password' TRUST_PROXY=true PORT=3333 pnpm dev
```

### Troubleshooting Auth

| Symptom | Cause | Fix |
|---|---|---|
| Domain accessible without login prompt | `TRUST_PROXY` not set → all requests classified as local | Add `TRUST_PROXY=true` to tmux start command |
| API returns 200 even with password set | Same as above | Same |
| Login page appears but login fails | Password mismatch or `!` not properly escaped in bash | Use single-quotes: `HERMES_PASSWORD='!mypass'` |
| Login returns 400 "Authentication not required" | `HERMES_PASSWORD` not picked up by process | Check tmux command — password may have been shell-expanded |

## Kanban Task-Board Unification (v2.3.0+)

The workspace task board (`/api/claude-tasks`) now reads from the **same SQLite DB** as `hermes kanban` CLI (`~/.hermes/kanban.db`).

### Requirements

- **`sqlite3` CLI must be installed:** `apt-get install sqlite3`
- **`CLAUDE_KANBAN_BACKEND=claude`** env var forces direct SQLite mode (needed when dashboard kanban plugin is unavailable)

### Backend Resolution

Priority order in `resolveKanbanBackend()`:
1. `CLAUDE_KANBAN_BACKEND` env var (local | claude | hermes-proxy)
2. Dashboard kanban plugin (port 9119 `/api/plugins/kanban/board`)
3. Direct SQLite to `~/.hermes/kanban.db` (via `sqlite3` CLI)
4. Local JSON fallback (`swarm-kanban.json`)

### Status Mapping (Workspace Lane → Kanban DB)

Controlled by `mapBoardStatus()` in `src/server/kanban-backend.ts`. Tasks flow through this function when the Workspace writes to the shared `~/.hermes/kanban.db`.

| Workspace Lane | Kanban DB Status | Dispatcher Behavior |
|---|---|---|
| `backlog` | `ready` | Picked up immediately (auto-dispatch) |
| `ready` | `ready` | Picked up immediately |
| `running` | `running` | Already claimed |
| `review` | `review` | NOT picked up (non-standard; dispatcher ignores) |
| `blocked` | `blocked` | Held until unblocked |
| `done` | `done` | Terminal |
| default | `todo` | Promoted→ready by `recompute_ready()` next tick |

### `mapBoardStatus` Bug — "queued" Status

**Symptom:** Tasks added from Workspace UI never auto-run, stuck with status `queued` in `hermes kanban list`. The dispatcher (`dispatch_once()` in `kanban_db.py`) only processes tasks with `status = 'ready'` — it does NOT recognize `queued`.

**Root cause:** `mapBoardStatus()` in `src/server/kanban-backend.ts` mapped `backlog` → `'queued'` and `default` → `'queued'`, neither of which are valid dispatcher statuses (valid: `triage`, `todo`, `ready`, `running`, `blocked`, `done`).

**Fix (already applied):**
```typescript
// In mapBoardStatus(), line ~286:
case 'backlog':
  return 'ready'   // was: 'queued'
// ...
default:
  return 'todo'    // was: 'queued'
```

**Manual recovery** for stuck tasks:
```bash
sqlite3 ~/.hermes/kanban.db "UPDATE tasks SET status = 'ready' WHERE status = 'queued';"
hermes kanban dispatch  # trigger immediate pickup
```

### Dispatcher (Task Execution)

Kanban tasks in `ready` status are automatically picked up by the dispatcher, which is **built into the Hermes gateway** (v2.3.0+). No separate daemon needed. The standalone `hermes kanban daemon` is deprecated and exits with a warning.

- Configure: `~/.hermes/config.yaml` → `kanban.dispatch_in_gateway: true` (default)
- Interval: 60 seconds between dispatch ticks
- Tasks **must have an assignee** to be picked up. Unassigned tasks stay in `ready` forever.
- Check activity: `hermes kanban stats` (watch task counts move: ready→running→done)
- Task logs: `hermes kanban log <task_id>`

See `references/kanban-unification.md` for full dispatcher lifecycle details.

### Troubleshooting
|---|---|---|---|
| Task board empty (even with data in kanban) | `sqlite3` CLI not installed | `apt-get install sqlite3` + restart workspace |
| Task board empty | Done tasks hidden by default | Use `?include_done=true` query param |
| Kanban UI shows "Failed to load tasks" but API works | All kanban tasks are `done` — `/api/claude-tasks` filters them out, frontend interprets empty array as error | Create at least one non-done task, or verify via `/api/swarm-kanban` (which returns all tasks including done) |
| Pull blocked by routeTree.gen.ts | Auto-generated file conflict | `git checkout -- src/routeTree.gen.ts` |
| Workspace not serving after update | Process still building | Wait ~8s, check `logs/workspace.log` |
| Domain returns 401, but :3333 direct works | Nginx `auth_basic` still active from old setup | `sed -i '/auth_basic/d' /etc/nginx/sites-enabled/hermes.rachkun.dev && nginx -t && systemctl reload nginx` |
| Workspace v2.3.0 shows errors after pull | Hermes Agent outdated (workspace needs newer gateway) | `hermes --version` — if >100 commits behind, run `hermes update` |
| Files API 500: "No valid workspace selected" | `/root` is a blocked system path; workspace catalog can't fall back to `~/workspace` or `~/work` | Set `HERMES_WORKSPACE_DIR=/root/projects` (or any non-blocked path) when starting the workspace |
| Task stays "ready" forever, never runs | Task has no assignee — dispatcher skips unassigned tasks | `hermes kanban assign <task_id> <profile>` (e.g., `default` or `backend-eng`) |
| "Failed to load tasks" when clicking "Show Done" | `tasks-api.ts` probe calls `/api/claude-tasks` without `include_done=true` → all tasks done → count=0 → resolves to non-existent `/api/hermes-tasks` endpoint → HTML instead of JSON | Patch `src/lib/tasks-api.ts` — see `references/frontend-probe-bug.md` |
| "hermes kanban daemon" exits with deprecation warning | Standalone daemon deprecated in v2.3.0; dispatcher is built into the gateway | Just run `hermes gateway` (already managed by watchdog). Tasks will auto-dispatch. |
| Not sure if dispatcher is working | No direct status command | `hermes kanban stats` — if tasks move from ready→running→done, dispatcher is active. Check task log: `hermes kanban log <task_id>` |
| Workspace Kanban assignee dropdown doesn't show \"default\" profile | `claude-tasks-assignees.ts` only scans `~/.hermes/profiles/` subdirectories; \"default\" profile lives at `~/.hermes/config.yaml` directly, not as a subdirectory | Patch `src/routes/api/claude-tasks-assignees.ts` — see `references/assignee-profile-fix.md` |

### Nginx Auth Conflict (post-update)

After updating to v2.3.0, the workspace has its own password-based session auth (`HERMES_PASSWORD` / `CLAUDE_PASSWORD` env var). If the nginx config still has legacy `auth_basic` directives, you get double-auth: nginx returns 401 before the request even reaches the workspace. Symptom: `https://hermes.rachkun.dev` → 401, but `http://127.0.0.1:3333` → 200.

Fix: remove `auth_basic` and `auth_basic_user_file` lines from `/etc/nginx/sites-enabled/hermes.rachkun.dev`, then `nginx -t && systemctl reload nginx`.

### `/root` Blocked System Path (files API)

Workspace v2.3.0 blocks `/root` (and other system paths: `/bin`, `/etc`, `/usr`, etc.) as a workspace root. When running as root (`os.homedir() === '/root'`), the workspace catalog fallback chain (which tries `~/workspace`, `~/work`) hits the blocked path check and returns `isValid: false` with no path.

**Symptom:** `GET /api/files?action=list` returns 500 with `{"error": "No valid workspace selected"}`. The browser console shows the same error from `use-search-data.ts`.

**Fix:** Set `HERMES_WORKSPACE_DIR` to a non-blocked directory (e.g., `/root/projects`) when starting the workspace:

```bash
HERMES_WORKSPACE_DIR=/root/projects PORT=3333 pnpm dev
```

This must also be in the watchdog script (`/root/.local/bin/ensure-hermes-workspace.sh`).
